
============================================================
Scenario: catching contradictions with provenance, not guessing
============================================================

Problem:  add_entity_property_value is additive -- a second write for the same
          entity+property doesn't replace the first, it coexists alongside it.
          A lookup with no notion of provenance can't tell which value is current.
Solution: every write carries a source with an externally supplied `original`
          date. A lookup that checks provenance can resolve the conflict correctly.

------------------------------------------------------------
Step 1 -- seed 4 people, each with two conflicting TITLE values
------------------------------------------------------------
  Alice: wrote 'Software Engineer' (2020-01-15), then 'Staff Software Engineer' (2024-06-01)
  Bob: wrote 'Sales Director' (2019-08-01), then 'VP of Sales' (2023-11-12)
  Carol: wrote 'Data Analyst' (2018-03-20), then 'Principal Data Scientist' (2025-02-10)
  Dave: wrote 'Junior Developer' (2021-05-05), then 'Engineering Manager' (2024-09-30)

------------------------------------------------------------
Step 2 -- naive lookup vs. provenance-aware lookup, scored
------------------------------------------------------------
Person   Naive lookup                 Provenance-aware lookup      Correct value
Alice    Software Engineer            Staff Software Engineer      Staff Software Engineer
         ✗                            ✓                           
Bob      Sales Director               VP of Sales                  VP of Sales
         ✗                            ✓                           
Carol    Data Analyst                 Principal Data Scientist     Principal Data Scientist
         ✗                            ✓                           
Dave     Junior Developer             Engineering Manager          Engineering Manager
         ✗                            ✓                           

============================================================
Result
============================================================
Naive lookup:             0/4 correct
Provenance-aware lookup:  4/4 correct

The naive lookup isn't wrong by chance -- it doesn't know a conflict exists at
all, so it just returns the first HAS_PROPERTY edge it walks. The provenance-aware
lookup used nothing but the source_original dates on get_metadata's evidence
records, no LLM involved.

------------------------------------------------------------
Bonus -- validate() surfaces the same conflict conversationally (needs an LLM)
------------------------------------------------------------
validate("Alice's title is Software Engineer.")
  supporting:
    Alice . TITLE = 'Software Engineer'   <- resume-2020.pdf (2020-01-15)
  counter:
    Alice . TITLE = 'Staff Software Engineer'   <- performance-review-2024.pdf (2024-06-01)
Both stored values come back as evidence, each traced to its source --
validate() surfaces the conflict rather than silently picking one.
